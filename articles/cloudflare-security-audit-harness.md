Cloudflareが公開したセキュリティ監査スキルを、自分のリポジトリに対して3回回しました。スキル自体はよくできています。検証まで含めて本物のバグが出ました。ただし、そのままでは動きませんでした。理由はスキルの不出来ではなく、スキルが前提にしている実行環境が自分の環境と違ったからです。

足したのは3つです。サブエージェントを起動できる実行系、対象コードを実行するためのOSレベルのサンドボックス、そして成果物を検証する親側の作業です。作業時間の大半はこの3つに消えました。同じところで止まる人が多そうなので、実際に動いた構成を残します。

なお本記事は英語版（[agentjournal.dev](https://agentjournal.dev/blog/cloudflare-audit-skill-harness/)）の内容を日本語で書き直したものです。

## スキルが前提にしているもの

スキルは6フェーズで動きます。偵察（アーキテクチャとカバレッジ台帳の作成）、カバレッジ主導の探索、候補ごとの反証検証、構造化出力（`findings.json`）、記録の独立検証、レポート生成です。判定は `confirmed` / `needs_validation` / `rejected` の3種類で、確証が持てないものは severity を付けずに未解決事実として残す設計になっています。

リポジトリに書かれている要件は3つです。ツール利用と並列サブエージェントに対応したコーディングエージェント、validator を動かす Node.js、そして外部ネットワーク遮断・許可制の環境変数・リソース制限・書き込み先の制限を備えたOS強制のサンドボックス。

最後のひとつが助言ではなく前提なのが要点です。サンドボックスが揃わなければ、スキルは対象コードを実行せず、該当する指摘を `needs_validation` に落とします。対象のテストスイートを野放しで実行する監査は、手順の多いサプライチェーン事故なので、この判断は正しいと思います。

## 足したもの1: サブエージェントを起動できる実行系

スキルは作業を委任します。1つのエージェントが逐次探索すると日単位かかり、さらに自分の成果を自分で検証する構造になります。手元のCLIを3つ試した結果です。

| 実行系 | 結果 |
| --- | --- |
| pi | task ツールが無く、サブエージェントを起動できない |
| Command Code | task はあるが、クォータ制限で監査が途中停止した |
| opencode (V1) | skill・task・permission が揃い、3回とも完走 |

決め手はロール分離でした。`security-hunter` と `security-verifier` の2つをサブエージェントとして定義し、どちらもコードに対して読み取り専用にします。verifier は `task: false` にして子エージェントを起動できないようにしました。見つけた本人が検証まで担えない構造を、設定で担保する形です。

## 足したもの2: OSレベルのサンドボックス

軽い選択肢として bubblewrap を先に試しましたが、Ubuntu では `loopback: Failed RTM_NEWADDR` で即座に失敗しました。原因は非特権ユーザー名前空間を制限するカーネル設定（`kernel.apparmor_restrict_unprivileged_userns=1`）で、bwrap は自分のネットワーク名前空間を作れません。Docker に切り替えました。

Docker 側でも3つつまずきました。1つ目、`--tmpfs` は既定で `noexec` なので、scratch 配下のビルドが権限エラーで落ちます。マウントオプションに `exec` が必要です。2つ目、`debian:bookworm-slim` に `sqlite3` が入っておらず、対象のテストがデータベース系で軒並み失敗しました。セキュリティと無関係なノイズです。3つ目、`GOTOOLCHAIN=auto` はツールチェーンをダウンロードしようとするため、ネットワーク遮断下では必ず失敗します。`local` に固定し、`go.mod` と一致する `GOROOT` を読み取り専用で渡し、依存はホスト側で vendor してからスナップショットを取ります。

起動行は要点だけ抜くと次の形です。

```bash
docker run --rm --network none --read-only \
  --tmpfs /scratch:rw,exec,size=2g,mode=1777 \
  --mount type=bind,src=$SNAPSHOT,dst=/target,readonly \
  -e GOTOOLCHAIN=local -e GOFLAGS=-mod=vendor -e CGO_ENABLED=0 \
  --user 1000:1000 --cap-drop ALL --security-opt no-new-privileges \
  --memory 2g --cpus 2 --pids-limit 256 \
  local/audit-runner:1 /bin/sh -c 'cp -a /target/. /scratch/t/ && cd /scratch/t && <command>'
```

対象は読み取り専用でマウントし、実行ごとに書き込み可能なコピーを scratch に作ります。スナップショットは `git archive` から取るので、監査対象は1つのコミットに固定されます。`.git` が無いため、指示書に source ref を明記しないと「何を監査したか」を後から言えなくなります。

## 足したもの3: 成果物を検証する親の仕事

validator 2本（カバレッジ台帳と findings のスキーマ検査）は、エージェントではなく親が実行します。ここを通さないと、構造だけ整った意味のないレポートが出てきます。

同じ理屈を指摘本体にも適用しました。委任されたエージェントの `confirmed` は主張であって事実ではありません。確証とされた項目ごとに、修正前のコミットに対して再現テストを自分で書き、同じテストを修正後のコミットで流しました。修正前が赤、修正後が緑、を確認して初めて「直った」と扱います。

## 所要時間と、1回では足りないという話

中規模のGoリポジトリでの実測です。

| プロファイル | 実時間 | エージェント数 |
| --- | --- | --- |
| quick（範囲限定） | 約40分 | 少数 |
| quick（全体） | 約52分 | 19 |
| standard（全体） | 約2.9時間 | 最大60 |

スキルの記述にもありますが、1回の実行では繰り返し実行して見つかる全体のおよそ半分しか拾えません。自分の計測でも同じ傾向で、2回目・3回目で初めて出た指摘があり、しかも1回目に棄却したものが3回目で high として確定する場面がありました。プロファイルは速度設定ではなくカバレッジの設定だと考えるべきです。

## 運用上のつまずき

いちばん痛かったのは、委任エージェントが動いている最中に `git checkout` をしたことです。エージェントは古いHEADを読み続け、存在しないコードに対する指摘を作りました。ブランチ操作は監査の前後にまとめて行い、実行中は触らないのが鉄則です。

出力先はリポジトリの外に置きます。スキルの既定はホーム配下の専用ディレクトリで、これは対象リポジトリを汚さないための設計です。

ここまで揃えてようやく、監査は「回る」状態になりました。スキル単体は良くできていますが、実行環境まで含めて初めて道具になります。同じスキルを自分のリポジトリで試したことはありますか？ 止まったのはサブエージェントとサンドボックスのどちらでしたか？
