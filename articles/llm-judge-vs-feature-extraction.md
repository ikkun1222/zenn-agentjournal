テキストと質問リストを渡すと0〜1のスコアを返す判定APIを、分類タスクでどう使うか。選択肢は2つあります。1行につき1つの問いを投げて閾値で切る「直接判定」と、1行につき12〜14の観点をスコアリングし、その生スコアを自分のラベルで学習した線形モデルに入れる「特徴量抽出（分解）」です。

この2つを実測しました。最初に作った合成データ2本、公開データセット2本（プロンプトインジェクション検出、日本語NLI）、そして手元の実データ1本（会計の仕訳エクスポート）。テスト行数は5,500行、入力トークンは3,410万、APIの実費は1.43ドルです。

結論を先に書きます。分解が効くのは、1つの問いがすでに弱いタスクだけでした。それ以外の場所では、トークンを2倍払って誤りの性質を悪化させます。

この記事で書くのは結論だけではありません。最初に作ったテストは自分で無効にしてしまい、分割の設計を間違えて精度を8ポイント読み違え、無料のn-gramベースラインと引き分け、最後は実データで「安い方が勝つ」ところまで来ました。順番そのものに情報があるので、時系列で残します。

## 何を測ったか

| タスク | 難所の作り方 | 学習 / テスト |
|---|---|---|
| 合成1: B2B返信の実質YES/NO（200行） | 32のテンプレート族。「we'll pass」を含むYES行、「absolutely」を含むNO行を混ぜた | 100 / 100 |
| 合成2: 文体アトリビューション（300行） | 名前も語彙も手がかりにならず、弱い手がかりの集積だけでラベルが決まる | 300行を交差検証 |
| プロンプトインジェクション検出 | 難問ベナイン339件（手法に言及するだけの正常文）＋外部セット2,060行 | 4,391 / 942 |
| 日本語NLI（JNLI、JGLUE） | entailment / contradiction / neutral の one-vs-rest | 8,000 / 2,434 |
| 仕訳行 → 借方勘定科目 | 実データの会計エクスポート、上位12科目（全体の87%） | 4,907 / 2,101 |

ベースラインは無料かつローカルです。文字2/3-gram、単語bigramのNaive Bayes、多数クラスを用意しました。比較は同一行に対するMcNemar検定とペア付きブートストラップ区間で行っています。

| タスク | 直接判定 | 12〜14次元＋重み | 最良のn-gram |
|---|---|---|---|
| インジェクション（テスト） | 0.837 | **0.952** | 0.954（単語bigram） |
| インジェクション（外部セット） | **0.956** | 0.840 | 0.381 |
| 難問ベナイン（全て正常） | **偽陽性率1.5%** | 偽陽性率37.2% | 偽陽性率14.2% |
| 日本語NLI | 0.837 | **0.908**（+7.0pt、p<1e-4） | 0.553 |
| 仕訳 → 科目（12択） | 0.400 | 0.911 | **0.949** |

## なぜ分解したくなるか — 運用面の魅力

分解の魅力は、統計的な期待より先に運用の都合として現れます。APIを叩く工程は抽出だけなので、ここをJSONLに全部キャッシュして途中再開できるようにしました。重みの学習はローカルで完結し、瞬間で終わり、追加課金がありません。

実際、公開データと実データを合わせた20,139行の抽出は、25,174コールを夜間に9分14秒で走り切って失敗は0件でした。以降の重み変更、閾値変更、特徴量の絞り込みはすべて無料です。「判定器を1問だけ呼ぶ」設計では、この試行錯誤のたびに全行を再判定することになります。

分解が勝つのが先か、この運用の快適さが目的化するのが先か。それが分からなくなるので、最初に素直なテストを置きました。

## 実測1: 最初のテストは自分で無効にした

合成データを200行作りました。B2Bの返信メールが「実質YES」か「実質NO」か。32個のテンプレート族から生成し、両側に罠を入れます。YES行に「今回は見送ります」を混ぜ、NO行に「ぜひ一度お伺いしたい」を混ぜる。文面だけを見れば逆に見える行を、多少は入れないと意味がありません。

結果、1問だけの直接判定が100%を取りました。私の12次元パイプラインは98%です。

つまりこのテストは無効です。自分の生成器に対して、1問で解けるタスクを引いてしまった。この時点で「分解は劣る」と結論するのは簡単ですが、それも間違いです。どちらの方向にも使えないデータです。

## 実測2: 分割の設計ミスで8ポイント読み違えた

同じ200行を使い、今度は分割だけを変えました。行をランダムに分ける5分割交差検証では98%。テンプレート族ごと丸ごと学習から抜いて評価すると90%です。

文字2-gramのNaive Bayesを同じ族分割で回すと93.5%でした。

ここで起きていたのは、テンプレートの言い回しを覚えることによる見かけの実力です。9割の精度を出している特徴量は、同じ言い回しを見たことがあるかどうかを測っていました。以後、テンプレートや生成元の族で分割することを先に決めてから、モデルを回しています。

## 実測3: 1問では解けないタスクを書く

合成データを作り直しました。300行の文体アトリビューションです。名前も、語彙も、決定的な1文も手がかりになりません。ラベルは弱い手がかり（構造化の度合い、見出しの有無、句読点の癖、敬体の混ざり方など）の集積の中にだけ存在します。

直接判定には不利な条件を出しませんでした。クラスの文体説明を渡し、12択を1問で聞きます。

- 直接判定: **64.7%**
- 12次元＋学習した重み（交差検証の外側予測）: **74.0%**（+9.3pt、McNemar p=0.0050）
- 参考: 最良の単一次元 `structuring` だけ: 66.0%

同時に、判定APIの自己申告の自信が使えないことも分かりました。300行のうち126行（42%）で、直接判定は0.9以上の自信を返しました。その126行での正解率は72.2%です。自信と正しさが乖離するのは、タスクが難しくなる場所でした。自信を閾値に使いたい場所で、まさにそれが壊れている、という結果です。

ついでに確認したことが2つあります。選択肢の順序を入れ替えても直接判定は64.7%で完全に同一でした（選択位置のバイアスなし）。`noul` の向きもドキュメントではなく実測で確認しました。真の文が0.96、偽の文が0.02です。

## 実測4: 無料のn-gramと引き分ける

同じ300行、同じ分割で、文字2-gramのNaive Bayesを回しました。74.0%。14のAPI次元にロジスティック回帰をかけた数値と完全に一致です。

文体のような表層の手がかりが正解を決めるタスクでは、次元分解は「n-gramの再発明」をAPI越しに高コストでやっていることになります。次元を設計する前に、テキストから直接取れる安い特徴量でベースラインを引かないと、自分の改善が何を測っているのか分からなくなります。

## 実測5: 日本語NLI — 語彙的な近道がないタスク

日本語NLI（JNLI）を8,000行で学習し、2,434行で評価しました。3クラスを one-vs-rest で分解しています。

- 次元モデル: **0.908**（macro-F1 0.885）
- 直接判定: 0.837（+7.03pt、95%CI [+5.67, +8.38]）
- 全てのn-gramベースライン: 0.499〜0.553（多数クラスが0.553）

n-gramが多数クラスを超えられないタスクでは次元が明確に勝ちます。誤りの内訳も特徴的で、contradictionクラスでは次元が0.921、直接判定が0.654でした。

もう1つ、語彙の重なりで層別すると挙動が分かれます。2文がよく似ている（Jaccard上位帯）行では直接判定が伸びず、次元モデルは重なりが大きいほど強くなりました（0.80以上の帯で0.987）。

リーク検査も先に置いています。学習とテストの間で前提＋仮説の完全重複は0件、前提文だけの重複が21件。この0.908は記憶ではありません。

## 実測6: 実データ（仕訳 → 借方勘定科目）

手元の会計データで、1行（摘要・金額・貸方科目・貸方補助科目）から借方の勘定科目を当てるタスクを組みました。12択です。

前提として2つ処理しています。まず、出力側に近すぎるフィールドは入力から外しました。この手のエクスポートには借方補助科目が入っており、これは実質ラベルそのものです。もう1つ、全科目は55クラスありますが上位12科目が全体の87.4%なので、タスクをそこに限定し、評価もその範囲で読むことにしました。

- 直接判定（12択を1問）: **0.400**
- 14次元＋学習した重み: **0.911**
- 単語bigramのNaive Bayes: **0.949**

分解は+51pt伸びました。ただし勝ったのはn-gramです。摘要テキストが科目をほぼ決めており、同じ摘要が複数の科目に対応する行は3.8%しかありません。この条件では安い方が勝ちます。

（このタスクの元データは実取引なので、記事には行の中身を出しません。件数と評価だけを扱います。）

## 誤りは直交する

仕訳タスクで面白かったのは、この2つのモデルが同じ行で間違っていないことでした。n-gramだけで解けた行が138、次元だけで解けた行が63あります。

そこでn-gramの12クラス確率を14次元の隣に並べて学習（スタッキング）すると、**0.970**（+2.33pt、95%CI [+1.57, +3.14]）になりました。どちらが勝つかを決めるのが目的ではなく、同じ行で失敗するかどうかを測るのが先です。

なお、直接判定の確率を13番目の特徴量として混ぜるのは勧めません。校正が壊れ（偽陽性率46.0%、外部セットの精度は0.956→0.788）、良い直接判定は独立した判定者として残すべきです。

## 代償は偽陽性 — 4回試して4回失敗した

「手法に言及しているだけの正常文」339件を用意して、正常側の誤検知を測りました。セキュリティの解説記事やドキュメントが該当します。

- 直接判定: 偽陽性率 **1.5%**
- 12次元モデル: 偽陽性率 **37.2%**（約25倍）
- 単語bigram: 偽陽性率 43.4%

原因は明白でした。学習された重みの最大の正係数は `obfuscated_encoding`（+1.80）と `hidden_in_content`（+1.62）で、その次元の名前のまま、解説文が該当してしまう。そこで4つ試しました。全部失敗しています。

| 試したこと | 結果 |
|---|---|
| 難問ベナイン170件を学習に追加 | 37.2% → 34.3% |
| 表層的な次元を落とす | 40.7% に悪化 |
| 偽陽性率5%目標まで閾値を締める | 攻撃検出が0.952 → 0.770（−18pt） |
| 直接判定の確率を13番目の特徴量に追加 | 46.0% に悪化、外部セットも悪化 |

これは重みの問題ではなく、次元の設計の問題です。私の次元は「難読化されているか」「入力の中に指示が埋まっているか」を聞きます。攻撃手法を引用している解説文は、その両方にyesと答えます。「その手法を**使っている**のか、**論じている**だけなのか」を分ける次元を、私はまだ書けていません。これが次の検証課題です。

## 個別の精度表ではなく、内訳を読む

手法ごとに精度を1つだけ見ると、判断を間違えます。外部セット2,060行を発生源で割ると挙動が分かれます。

- hackaprompt系の攻撃文字列: 直接判定 0.665 / 次元 0.977
- ある部分集合: 全ての手法が0.63〜0.67（手法差ではなく共通の天井）
- 外部セット全体: 次元モデル0.840、n-gramは0.381まで崩壊

特に効いたのは「全ての手法が0.63〜0.67に沈む部分集合」の存在でした。ここは手法の選択ではなくデータの難易度の問題です。平均だけを見ていたら、次元の改善余地と難所の存在を見落としていました。

## 運用で分かったこと

- 全20,139行の抽出（25,174コール）は夜間に9分14秒、失敗0件。並列化とJSONLの途中再開で、途中で止めても翌晩に続きから進みます。
- 唯一のエラーは自分のものです。質問オブジェクトから必須フィールド（`instructions`）が抜けていて、CLIが終了コード1でフィールド名を返しました。勝手に別のことを判定しない設計になっていたのが功を奏しました。
- 再開時の出力は追記ではなくマージです。全行が既に評価済みの状態で再実行すると、`skipped: 300 / extracted: 0` を返して即座に終わります。
- 効かない次元は容赦なく0になります。敬体比率の次元は分散0.009（AUC 0.514）で、L2正則化のもとでは重みがほぼ0になりました。次元は多いほど良いのではなく、効かない次元は自分で消えます。
- 交差検証の数値は独立実装でも確認しました。自分の実装で74.0%（AUC 0.811）、numpyで書き直した実装で73.7%（AUC 0.809）。学習の実装はここまで一致します。

## コストの内訳

入力単価は100万トークンあたり0.042ドルで、API自身の利用カウンタから読み取りました。

| 方式 | トークン / 行 | ドル / 1,000行 | ドル / 100万行 |
|---|---|---|---|
| n-gram / TF-IDF | 0 | 0 | 0 |
| 直接1問 | 444〜619 | 0.019〜0.026 | 19〜26 |
| 12次元 | 1,010〜1,036 | 0.042 | 42 |
| 14次元 | 1,136〜1,154 | 0.048 | 48 |
| スタッキング（次元＋n-gram確率） | +0 | +0 | +0 |

次元1つあたり40〜50トークンで、その大半は問い自体の文言です。12次元は1行あたり1,010〜1,036トークン、直接1問（444〜619トークン）の1.6〜2.3倍で、月100万行なら42ドル対19〜26ドル。3タスク全体の実験は3,410万入力トークンで1.43ドルでした。抽出は一度きりなので、学習用の4,391行は0.19ドル、その後の再学習は0ドルです。

請求額の側にお金はありません。月100万行・正常トラフィック20%という条件では、偽陽性率37.2%は約74,000行が人手レビューに回ることを意味します（1.5%なら約3,000行）。その差は約590時間の作業です。トークン代を月20ドル前後節約するために590時間を積み増すのは、桁を間違えた最適化です。

## 現在の運用フロー

| 手順 | 確認すること | 打ち切り条件 |
|---|---|---|
| 0 | ラベル付き200行（可能なら実データ） | — |
| 1 | n-gram / TF-IDFのベースライン | 目標達成 → 判定APIは不要 |
| 2 | 1行1問の直接判定 | 精度0.95以上 → 分解は改悪 |
| 3 | 次元＋学習した重み | 語彙的な近道がないタスクに限る |
| 4 | 次元とn-gram確率のスタッキング | 誤りが直交するとき+2.3pt |
| 5 | 直接判定を主、次元をセカンドオピニオンに | 難問ベナインで必ず学習する |

ガードレール用途では、厳しめの閾値で直接判定を1回呼び、その判定が不確かな行だけ小さな次元モデルに相談します。分類はn-gramを先に置き、残差に次元を積む構成です。多クラスでは12択を1問で聞かないこと。今回の計測で最悪の結果でした。

## 限界と注意点

- 12〜14次元は自作なので、この数値は筆者の次元設計を説明するものです。「手法に言及している」と「手法を使っている」を分ける次元が、偽陽性の次の検証課題です。
- 日本語NLIのラベルにはノイズと55%のneutral偏りがあるため、0.908は上限ではありません。外部インジェクションセットには類似行に矛盾するラベルがあります。
- 仕訳タスクは上位12科目が対象で、入力に貸方側の科目も含みます。素の銀行明細ではなく「文脈付きで取り込む」ケースです。55クラス全体では難易度が上がるため、この数値はそのまま拡張できません。
- 結果は3タスクの計測であり、次元の設計や閾値の決め方を変えれば数値は動きます。
- 出力トークンは価格に含めていません。CLIは入力のみを報告するため、846,765トークンを別途計測しています。

## まとめ

まず最も安いベースラインを書いてください。n-gramが通れば判定APIは不要です。1つの問いが0.95に届くならそれを維持します。分解は1.6〜2.3倍のコストで、正常入力を約25倍誤検知します。次元スコアは1つの問いが本当に弱いタスクにだけ使い、置き換えるのではなく安いモデルと積んでください。

順序の意味は単純です。安い工程から試し、効果が確認できた段階でだけ次の工程を足します。判定APIは最初に置くものではなく、n-gramと1問の直接判定が失敗したときに初めて使う工程という位置づけになります。

ここまでで測った範囲では、単一の問いが弱くないのに分解が勝ったタスクはありませんでした。今回の計測は入力トークン3,410万・実費1.43ドルで、生データと再現手順は英語版の [agentjournal.dev](https://agentjournal.dev/blog/llm-judge-vs-feature-extraction/) にまとめています。心当たりのある方がいれば、次元は問いが知らない何を知っていたのか、教えていただけると助かります。あなたのタスクなら、最初の1問はどう書きますか？
